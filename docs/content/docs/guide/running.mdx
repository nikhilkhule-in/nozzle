## Invocation

```bash
cargo run -p nozzle-run -- run <workflow.yaml>
# or, with the justfile:
just run-demo
# or, once the CLI is installed (`cargo install --path runner`), by name:
nzl run <workflow.yaml>
# or, each task in its own container:
nzl run --executor docker <workflow.yaml>
```

The CLI has two subcommands plus help: `run`, which takes a workflow file path (with optional `--executor local|docker`, default `local`),
`schema`, which prints the workflow JSON Schema, and `help [subcommand]`. `nzl --help`, `nzl -h`, `nzl help`, `nzl run --help`, and
`nzl schema --help` print to stdout and exit `0`. Anything else prints
`usage: nzl [--help] <subcommand> [args]` to stderr and exits `2`.

## Executors

- `local` (default): `sh -c '<cmd>'` on the host, inheriting ambient env plus data-flow `env` bindings. `image` is ignored.
- `docker`: `docker run --rm --entrypoint sh -v <vol>:/work -w /work --name nozzle-<run>-<task> <image> -c '<cmd>'` per task on the Docker host. Each task needs `image:`; containers see only `passEnv` allowlist entries plus data-flow `env`. One anonymous volume per run is mounted at `/work` and removed even on failure. Daemon comes from `DOCKER_HOST` or the default socket — unreachable daemon exits `2` before any task runs.

See `examples/release.yaml` for the self-CI pattern: `clone` with `alpine/git` onto `/work`, then `test`/`clippy` on `rust`, smokes on `python`/`node`, all sharing the work volume.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Every task reached `succeeded` |
| `1` | The run executed but ended `FAILED` (a task failed, or tasks stayed blocked) |
| `2` | Could not run at all: usage error (including unknown executor), unreadable file, invalid workflow, missing image in Docker mode, missing `passEnv` var, or unreachable Docker daemon |

Scripts should branch on the code, not on parsing stdout. The
[CLI reference](/docs/reference/cli) is the exhaustive contract, including
`nzl schema`.

## Output anatomy

```text
-> gen-tag: sh -c 'echo "..."'              ← start: the command, verbatim from YAML
<- gen-tag: succeeded in 0.0s               ← end: terminal state + wall time
-> build: sh -c 'docker build -t "$IMAGE_TAG" examples/context'
<- build: succeeded in 1.4s
-> verify: sh -c 'docker image inspect "$IMAGE_TAG" > /dev/null'
<- verify: succeeded in 0.1s
== run 'build-random-image' SUCCEEDED ==    ← verdict line
   gen-tag: succeeded in 0.0s               ← per-task table, definition order
   build: succeeded in 1.4s
   verify: succeeded in 0.1s
```

Notes on the failure shapes:

```text
<- a: failed in 0.0s (exit status 3)            ← non-zero exit of the command
<- big: failed in 0.0s (output of 140000 bytes
   exceeds inline-only threshold of 65536 bytes) ← data-flow guard tripped
<- b: failed (blocked by upstream failure)      ← never executed
```

Important: only `->`/`<-` lines and the summary go to the runner's stdout.
**Task stderr is inherited**, so whatever the command prints to stderr —
docker progress, compiler warnings — streams live and unmodified. Task stdout
is captured, not shown: its job in life is to feed downstream variables.

## Data flow between tasks

For `env: { VAR: upstream }` on a task:

1. When the upstream reaches `succeeded`, its stdout is captured with all
   trailing newlines (`\n`, `\r\n`) trimmed — exactly one line of shell output
   becomes one clean variable value.
2. The variable is injected into the downstream process, **overriding any
   ambient value** of the same name: bindings win over the environment you
   invoked `nzl` with.
3. Optionally, the value is checked against the inline threshold (64 KiB by
   default). Oversized values are refused outright — see
   [execution semantics](/docs/guide/execution-semantics#the-size-guard).

Multiple bindings on one task are all injected (each is its own edge), and a
task may bind from several different upstreams — a fan-in.

## Timing

Durations are wall-clock `Instant` spans around the whole attempt, from just
before spawning `sh` until exit or placement verdict. Sub-second times print
like `0.0s`, so treat them as coarse order-of-magnitude lines — the summary is
for humans, not for benchmarking.
