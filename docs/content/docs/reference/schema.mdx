`schemas/workflow.schema.json` is the machine-readable contract of the
workflow format. It is **generated, never hand-maintained**:

```bash
just schema    # cargo run -q -p nozzle-run -- schema > schemas/workflow.schema.json
```

The command runs `nzl schema`, which serializes the loader's own Rust types
(`runner/src/model.rs`) with `schemars`. Because the schema is derived from
the types the engine actually parses with, it cannot drift from what the
engine accepts. Output is byte-deterministic — diffs contain only your real
type change.

## Properties

| Property | Value |
|---|---|
| Draft | 2020-12 |
| Covers | `WorkflowYaml` / `TaskYaml` — the full YAML surface |
| Applicability | `.yaml`, `.yml`, and `.json` files (JSON is a subset of YAML) |
| Generated by | `nzl schema` / `just schema` |

## What it checks — and what it deliberately does not

The schema mirrors the loader's field checks:

- non-blank `name`, `id`, and `cmd`
- at least one task
- `env` values must be strings
- unknown fields pass through unchecked (the loader ignores them, and the
  schema reflects that same tolerance)

It intentionally does **not** check cross-references — duplicate task ids,
`needs`/`env` naming nonexistent tasks, and cycles are **runtime
validations**, because JSON Schema cannot express them. Those are enforced by
the core's graph validator with aggregated error reporting; see
[validity rules](/docs/reference/yaml-reference#validity-rules).

## Using it in an editor

Add a header comment to any workflow file:

```yaml
# yaml-language-server: $schema=../schemas/workflow.schema.json
name: my-workflow
```

A repo checkout wires it automatically: `.vscode/settings.json` maps the
schema to `examples/**`.

## Regeneration discipline

When `runner/src/model.rs` changes, rerun `just schema` and commit the
result. The committed file is the contract that editors, external tools, and
future SDK code generators consume; `nzl schema` is the only thing that
produces it.
